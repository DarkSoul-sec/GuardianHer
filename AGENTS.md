# AGENTS.md

Flutter application (Dart SDK `^3.13.0`, Flutter >= 3.18). Clean Architecture with Riverpod (2.x) state management and go_router navigation. Features live in `lib/features/<name>/` split into `domain/`, `application/`, `data/`, `presentation/`; platform plugins are behind interfaces composed in `lib/core/providers.dart`.

## Commands

- `flutter pub get` — resolve dependencies (run after editing `pubspec.yaml`)
- `flutter analyze` — static analysis (uses `flutter_lints` via `analysis_options.yaml`)
- `flutter test` — run the widget test suite
- `flutter run` — launch the app (hot reload = `r`, hot restart = `R`)
- Test count expectation: 482 passing (462 after Phase C; +20 net new Phase D Vehicle Information tests) plus 36 backend tests (`cd backend && python -m pytest tests -q`).

## Gotchas

- Analyzer excludes all `build/` and platform directories; only `lib/` and `test/` are linted.
- Dart 3 shorthand syntax is used in template code (e.g. `colorScheme: .fromSeed(...)`), so dot-shorthands compile fine on this SDK.
- Notification tap routing is centralized: `lib/core/platform/local_notifications.dart` exposes one shared plugin (`flutterLocalNotificationsPluginProvider`), an idempotent `ensureLocalNotificationsInitialized`, and a `localNotificationsTapHandler` dispatch global set in `lib/main.dart` (payload `check-in` → `/check-in`, else `/sos`). Never create a second plugin instance or a second tap callback.
- Check-in reminder scheduling uses `zonedSchedule` with `AndroidScheduleMode.inexactAllowWhileIdle` — no `SCHEDULE_EXACT_ALARM` permission is requested, so reminders may drift a few minutes; do not switch to `exact`/`alarmClock` without adding the manifest permission + runtime request.
- The timezone package requires the device IANA zone via `flutter_timezone` (see `FlutterLocalNotificationsCheckInScheduler._ensureTimeZone`).
- Home-screen SOS widget is a pure launcher: native `SosWidgetProvider` (`android/`) opens the app with a `guardianher://sos` URI; `lib/core/platform/home_widget.dart` routes cold (via `initiallyLaunchedFromHomeWidget`) and warm (`widgetClicked`) launches to `/sos`, wired in `GuardianHerApp.initState`. The widget never captures location or runs app logic in the background.
- Shake SOS (Phase 3E) is a deliberate, user-opt-in **exception** to the "no foreground service" rule: `android/.../ShakeSosService.kt` keeps the accelerometer running while the app is closed and launches the app with a `guardianher://shakesos` URI when a deliberate shake (3 quick shakes) is detected. `home_widget.dart` routes that URI to `/sos` **and** arms SOS via the `onShakeSos` callback passed to `setupWidgetLaunchRouting` (widget taps navigate only, never arm). The detector shows a persistent low-priority notification and requires `FOREGROUND_SERVICE` + `FOREGROUND_SERVICE_SPECIAL_USE` (manifest, no runtime prompt). Tuning constants (threshold, window, counts, 10 s cooldown) are all in `ShakeSosService.kt`; tune on the Redmi, not the emulator. The service logs diagnostics to logcat under tag `ShakeSosService` (shake detected / cooldown suppression / launch). Settings > Shake SOS enables/stops the service (persisted as `shake_sos_enabled`) and links to battery-optimization settings — Redmi/MIUI kills the service unless whitelisted.
- **Root cause of "shake works only with the app open": Android's background-activity-start restriction.** A foreground service is NOT an exemption — when the app is fully closed, the service detects the shake and calls `startActivity`, but the OS refuses it (`ActivityTaskManager ... (BAL_BLOCK)`). The only user-grantable exemption is `SYSTEM_ALERT_WINDOW` ("Display over other apps"), which the Shake SOS settings screen now checks (`Settings.canDrawOverlays` via the `guardianher/shake_sos` channel's `canDrawOverlays`/`openOverlaySettings`) and links to `ACTION_MANAGE_OVERLAY_PERMISSION`. Granting it never shows an overlay; it only exempts the background launch. Without it, a closed-app shake is detected but silently does nothing.
- **SOS vibration is a repeating alert, driven by the OS, not a Dart timer.** `playSosAlert` plays `sosVibrationPattern` (`[0,300,200,300,200,300,4000]`) with `repeat: 0`, so the OS loops the burst+gap cycle until `stop()` cancels it — this works with the screen off and the app backgrounded, and there is no Dart `Timer` to leak in widget tests. When the Shake SOS service is running, `SosActionController._startAlert` hands the alert to the native service (`guardianher/shake_sos` channel `startSosAlert`/`stopSosAlert`) so it survives the process being killed; the service mirrors the pattern as `VibrationEffect.createWaveform(SOS_ALERT_PATTERN_MS, 0)`. **The native service ALSO engages the loop directly in `ShakeSosService.triggerSos()` at shake detection** — that is what makes the alert work when the app was fully swiped away: `startActivity` can be refused (no `SYSTEM_ALERT_WINDOW`), so Dart may never run, and the native-first vibrate covers that path. `GuardianHerApp.initState` calls `stopSosAlert` at boot to clear any loop left behind by a killed session (the shake-URI routing re-arms it via `startSos`). Note: under `flutter test` (`FLUTTER_TEST` env), `defaultTargetPlatform` is forced to android — tests must override `shakeSosServiceProvider` (the central `defaultOverrides` in `test/helpers/fakes.dart` does) or the controller would hit the real channel and hang.
- **SOS auto-enables location when it is off.** `SosActionController._ensureLocationEnabled` runs before the capture: if services are off it tries a silent native enable (`guardianher/location` channel `enable` in MainActivity), which only succeeds for the device owner or an app granted `WRITE_SECURE_SETTINGS` (declared in the manifest; effective via `adb shell pm grant com.guardianher.app android.permission.WRITE_SECURE_SETTINGS` — the API is hidden, so `setLocationEnabledForUser` is invoked reflectively). When the platform refuses, it opens the system location settings so the user flips the switch in one tap, and the location retry (`sosLocationRetryDelayProvider`) now also fires on `servicesDisabled` to re-capture afterwards. Normal installs always get the settings-screen fallback — Android gives ordinary apps no other way.
- Contact phone numbers are stored digits-only. The contact form defaults the country code to `+91` (`CountryCode.defaultDialing`); `PhoneNumber.withDialingCode`/`stripDialingCode` combine and strip the prefix. Entering a number starting with `+` is treated as complete.
- **Phase 3G (Communication) — user-confirmed cascade, still no SEND_SMS / no auto-send.** All messaging goes through `CascadeCheckInMessageSender` (check-ins) or the location share flow: SMS composer → email composer (only if a contact has an optional email) → system share sheet; each channel's failure type drives the next step, and wording stays "opened", never "sent". Multi-recipient SMS URIs join with `,` and prefix every number with `+` (E.164) — do not regress to `;`. Contacts carry an OPTIONAL normalized email (document version stays 1; present-but-invalid email = corrupted data; empty update clears it). The manifest `<queries>` must keep the `SENDTO sms/smsto/mailto` entries — url_launcher uses ACTION_SENDTO and Android 11+ hides resolvable apps without them (the old VIEW-only declaration was the latent bug). `share_plus` (^13) backs the last-resort share sheet; under `flutter test`, override `shareServiceProvider` via the central fakes when testing flows that can reach it.
- Device administrator (Settings > Device administrator, opt-in, Android only): `android/.../DeviceAdminReceiver.kt` declares **no policies** — admin status is used only so the system blocks uninstall and disables "Force stop" while active, keeping the Shake SOS detector alive and the app hard to remove. MainActivity's `guardianher/device_admin` channel exposes `isActive`/`requestActivation`/`deactivate`; the settings screen refreshes status on lifecycle resume. It is NOT a system app and never locks/wipes; anyone can deactivate from Settings > Device admin apps. Do not add lock/wipe policies.
- The Shake SOS service survives task removal (`android:stopWithTask="false"` + `onTaskRemoved` re-anchors it); the cooldown is 10 s so re-tests work quickly.
- **Phase 3F (Background Safety Agent) — boot behavior and reminder alarms.** `RECEIVE_BOOT_COMPLETED` + three receivers are declared in the manifest: our `.BootReceiver` restores the shake detector after reboot / quick-boot / app update, reading a native flag (`guardianher_background` prefs, written ONLY by MainActivity's channel `start`/`stop` — internal re-anchors never touch it) so no Flutter engine is needed; `com.dexterous.flutterlocalnotifications.ScheduledNotificationReceiver` delivers each check-in alarm and `...ScheduledNotificationBootReceiver` re-registers them after reboot/update — flutter_local_notifications ≥16 no longer merges these itself, so **removing either declaration silently breaks reminders** (the alarm receiver was missing before Phase 3F; zonedSchedule could not fire on device at all). `BootReceiver` wraps the service start in try/catch: Android 16 field reports show `specialUse` FGS launches from BOOT_COMPLETED can throw `ForegroundServiceStartNotAllowedException` even though that type is not on Google's documented restriction list — a refusal logs and falls back to the Dart-side re-anchor (`ShakeSosSettingsController._restore`) on next app open. Receivers are exported=false (system broadcasts reach unexported receivers; protected broadcasts can't be spoofed). Battery guidance is status-aware: the shake_sos channel exposes `isIgnoringBatteryOptimizations` (PowerManager) and `manufacturerToken` (miui/coloros/funtouch/emui/magicos/samsung), mapped to OEM copy by the pure function in `lib/features/shake/domain/oem_background_guidance.dart`; both refresh on lifecycle resume. Do NOT add `REQUEST_IGNORE_BATTERY_OPTIMIZATIONS` (Play-restricted) or exact-alarm permissions.
- **SOS location capture (locked/backgrounded) is enabled by a location-type foreground service, not `ACCESS_BACKGROUND_LOCATION`.** `SosLocationService.kt` (`foregroundServiceType="location"`, `FOREGROUND_SERVICE_LOCATION` permission) is started via MainActivity's `guardianher/sos_location` channel when SOS activates and stopped on cancel/idle (`SosActionController._startLocationContext`/`_stopLocationContext`) and at boot in `app.dart`. Android 10+ grants background location to an app running a location FGS — the documented alternative to the background-location permission, which is intentionally NOT requested (nothing tracks continuously). The service does not obtain a fix; the Flutter capture flow (`LocationManagerLocationService`, GMS-free `guardianher/location_engine` channel) does. If the capture ends `unavailable`, the controller schedules ONE auto-retry after `sosLocationRetryDelayProvider` (15 s default, gated on SOS still active, cancelled on stop) — under `flutter test` any widget test ending mid-SOS with a failed capture must end the session (`cancelSos` → `fireComplete`) or the pending retry `Timer` fails the test. Under `FLUTTER_TEST` `defaultTargetPlatform` is android, so `sosLocationServiceProvider` must be overridden in the central `defaultOverrides` (`TestSosLocationService`) or SOS tests would hit the real channel.

## Phase 3D (Safety Check-In) invariants

- Scheduled reminder fires at the interval; the user confirms ("I am safe") to capture a one-shot **foreground** location and hand a message to the **user-confirmed** sender. No auto-send, no `SEND_SMS`, no foreground service, no background location — these are still out of scope (Phase 3G Communication will replace the `CheckInMessageSender` seam).
- A location failure never cancels a check-in: the message is still composed with an explicit "could not share my location" line.
- Missed check-ins escalate (re-notify + urgency wording) via the pure functions in `check_in_timeline.dart`; settings persist through `PreferencesCheckInSettingsRepository` (recipients stored as contact ids, never phone numbers).

## Phase 3H-3 (Scheduled Check-In Execution) invariants

- The scheduled fire now EXECUTES the pipeline, not just a reminder: `CheckInController.enable`/`acknowledge`/timeline-restore schedule through `CheckInScheduler.scheduleExecution` (payload `check-in-run`, same notification id 2001 upserted). Missed escalation still re-notifies with the reminder-style `scheduleReminder`.
- One shared pipeline: `runScheduledCheckIn(CheckInExecutionSeams)` in `lib/features/check_in/application/check_in_execution_service.dart` runs from BOTH the main isolate (`CheckInController.runDueCheckIn`, real SOS guard via `sosControllerProvider`) and the background isolate (`handleSafetyCheckInBackground`, `@pragma('vm:entry-point')`, hand-built seams, SOS flag trivially false because SOS cannot be active while the app is dead).
- Background dispatch goes through the top-level trampoline `localNotificationsBackgroundTrampoline` in `lib/core/platform/local_notifications.dart` — flutter_local_notifications rejects closures for `onDidReceiveBackgroundNotificationResponse`. Core never imports features; features assign `localNotificationsBackgroundHandler` from `main.dart` BEFORE first plugin init.
- Honest status model in `check_in_delivery_status.dart`: captured vs stale-only vs unavailable vs permissionDenied/servicesDisabled/timeout vs communicationFailed vs schedulerFailed. Nothing ever claims delivery — opening a composer is "waiting for you to send". Stale fallbacks are labeled LAST KNOWN with their capture time in the message body.
- Intervals are a CLOSED product-mandated set {60, 120, 180 min} in `check_in_interval.dart`; unknown stored minutes fall back to 60.
- Settings document is versioned (`version: 1` in `safety_check_in_settings_v1`); unsupported versions decode to safe disabled defaults, legacy docs without the field still load.
- SOS has absolute priority: an active SOS session makes the scheduled run record `skippedForSos` and reschedule; it never delays/cancels SOS.
- No new permissions and no new dependencies; unattended location capture from a fully-backgrounded app remains impossible by design (no ACCESS_BACKGROUND_LOCATION) — backgrounded runs record truthful statuses and leave the notification actionable.

## Phase 3H-3A (device validation) findings

- **The alarm does NOT spawn the Dart background isolate on delivery** (verified on Android 14/Motorola with instrumented entrypoint): flutter_local_notifications v22 posts the id-2001 notification from `ScheduledNotificationReceiver`, but `onDidReceiveBackgroundNotificationResponse` only fires for user-initiated responses. The scheduled tick's deliverable is therefore the NOTIFICATION; the pipeline completes when it is tapped — `CheckInScreen` auto-runs `runDueCheckIn` once per screen entry, gated on due/overdue state (a healthy cadence opening the screen does nothing).
- **Cold notification taps need explicit launch dispatch**: the plugin does not re-deliver a tap that LAUNCHED the process. `ensureLocalNotificationsInitialized` (called at startup from `GuardianHerApp.initState`, not lazily) must query `getNotificationAppLaunchDetails` and dispatch `localNotificationsTapHandler`; `main.dart`'s handler waits up to ~1 s for `publishedRouter` before routing (same pattern as widget launch routing).
- **The plugin REJECTS non-future schedule dates with `ArgumentError` (an `Error`)**: it escapes `on Exception` handlers and killed `_refreshTimeline` mid-flight on device (form desync + stuck unloaded state). The scheduler now clamps dates forward (`_clampFuture`) and catches all; `CheckInController._load` hard-fails safe to `loaded:true`.
- **`adb shell am force-stop` cancels AlarmManager alarms silently.** `refresh()` now ALWAYS re-asserts `scheduleExecution(nextDue)` (idempotent id-2001 upsert), so any app open heals a force-stopped cadence. `am kill` preserves alarms.
- Verified end-to-end on device: arm → process dead → alarm fires → notification posted → cold tap → `/check-in` route → pipeline runs → `locationCaptured` status persisted → next run rescheduled. Escalation (missed_count, urgency re-notify) observed live.

## Phase 3I (Location UX + WhatsApp fallback) invariants

- **SOS location section shows 7 truthful states** (`_SosLocationSection` in `sos_screen.dart`), with copy sourced from `LocationState.statusLabel`/`statusDetail` (single source of truth in `location_state.dart`): loading / captured (+accuracy) / stale ("Last known location" + "Updated X minutes ago") / servicesDisabled ("Location is turned off" + consequence line) / denied ("Location permission unavailable") / timeout ("Couldn't get your current location") / unavailable. `LocationStatus.timeout` is a DISTINCT enum value — the engine's `LocationTimeoutFailure` no longer collapses into `unavailable`; `formatAccuracy`/`formatCapturedTime`/`formatCapturedAge` live in `lib/features/location/domain/location_format.dart`.
- The SOS auto-retry (`_scheduleLocationRetry`) now also fires on `timeout`, not only `unavailable`/`servicesDisabled`. Still one retry, never for `denied`.
- **Coordinate-free session snapshot**: while SOS is active, every location change writes `SosLocationSessionStore` (prefs key `sos_location_session_v1`) via the listener in `SosActionController.build()` — session id, coarse state, capture epoch, accuracy, failure category ONLY (never lat/lng, URLs, contacts). Cleared on cancelling/idle transitions AND at app boot (`app.dart initState`): a dead session's leftovers must never look like live data.
- **WhatsApp targeting**: `PhoneNumber.toWhatsAppDigits` canonicalizes any input form to bare international digits (`09876543210`/`9876543210`/`+91 98765 43210` all → `919876543210`; numbers long enough to carry another country code pass through unchanged). It is a presentation-target rule only — storage stays digits-only E.164. The deep link uses the `whatsapp://send?phone=&text=` scheme (NOT https wa.me) so an unresolvable link surfaces as `NoWhatsAppAppAvailableFailure` instead of silently opening a browser tab; the manifest `<queries>` MUST keep `<package android:name="com.whatsapp"/>` + `com.whatsapp.w4b` or Android 11+ hides the handler and every attempt reports unavailable.
- **One launch per tap, no loops, no claims**: `WhatsAppService.openChat` reports only "chat could be opened"; registration state of the recipient is unknowable and never claimed. Failure opens a dialog titled "WhatsApp isn't available for this contact." offering [Send via SMS] (composer) and [Share another way] (share sheet). Entry point: Location screen captured view "Send via WhatsApp" → contact picker sheet (`whatsapp_share_flow.dart`); `FakeWhatsAppService` is overridden in the central test fakes.
- `buildLocationShareMessage` format: `GuardianHer SOS alert` / `Current|Last known location captured at HH:MM` / maps URL — stale fixes are ALWAYS labeled last known in share bodies too.

## Phase 3J (Real-time live location sharing) invariants

- **Feature is opt-in, honest, and off by default.** The API base URL comes from `--dart-define=GUARDIANHER_LIVE_API_URL` (`liveApiBaseUrl` in `live_location_api_client.dart`); an empty value (the default) makes every entry point show "Live sharing is not available in this build." — never a fake error. Sessions exist ONLY via explicit user start or an active SOS; there is no boot restore, no silent resume, no history.
- **Backend** (`backend/`, FastAPI + SQLAlchemy): token = `secrets.token_urlsafe(32)` (43 chars); the DB stores ONLY its SHA-256 hex digest (`app/tokens.py`), one latest point per session (`latest_locations` 1:1, replace-on-update), purged on expire AND revoke (lazy `_enforce_expiry` + lifespan `expiry_sweeper`). Public GET `/api/v1/live-sessions/{token}` returns byte-identical `{"status":"ended"}` for unknown AND expired tokens (no existence oracle; enforced by test); revoked returns `{"status":"revoked"}` so viewers see honest copy. Owner endpoints distinguish `404 not_found` / `410 expired` / `410 revoked`. Rate limits (in-memory fixed-window, injectable clock): create 5/h/IP, update 8/10s/token-hash, public read 30/min/(token+IP), stop 30/min/IP.
- **Web page** (`backend/app/static/live.{html,js,css}`): vanilla-JS slippy map rendering OSM raster tiles; the only third-party origin anywhere is `tile.openstreetmap.org`, pinned by CSP in `app/middleware.py` (+ `no-store`, `noindex`, `Referrer-Policy: no-referrer`). Transport is POLLING (5 s while tab visible) — deliberately not SSE/WebSocket. All logging goes through `PrivacyFilter` → `redact_message` (token-shaped segments and coordinate pairs are masked before any log line exists).
- **Android**: `LiveLocationService.kt` is a NEW location-type FGS (START_NOT_STICKY, "Sharing live location" notification) — do NOT generalize `SosLocationService`; the SOS path stays untouched. Engine gains `startLiveUpdates`/`stopLiveUpdates` streaming fixes over EventChannel `guardianher/location_updates` (GPS+NETWORK providers). Channel `guardianher/live_location` wires start/stop in MainActivity. No new dangerous permissions; still NO ACCESS_BACKGROUND_LOCATION (only an explanatory comment).
- **Client lifecycle**: session state lives ONLY in memory inside `LiveLocationController` — process death = interrupted, shown as "not sharing" on next launch. Upload loop pushes THE latest fix only (no backlog); offline capture continues and reports "Connection unavailable", retrying creation/push each tick; server-side expiry/revocation map to terminal statuses and stop all timers. Local TTL timer expires the session even without server contact. `stopSession` is idempotent and revokes remotely.
- **SOS integration**: `_activateEffects` fires `unawaited(_startEmergencyLiveLocation())` — SOS cadence 10 s, duration from `liveSosDurationProvider` (60 min); failure NEVER blocks or degrades SOS, and `sosMessageBodyProvider` appends `Live location: <url>` + `This link expires at HH:MM.` only when a URL actually exists. Under `flutter test` the central fakes override `liveLocationApiClientProvider` (unconfigured by default → unrelated tests fail fast if they touch it), `liveLocationUpdatesProvider`, `liveLocationForegroundServiceProvider`.
- **Tests**: widget tests that end mid-session MUST stop it (`stopSession`) or the pending TTL/upload timers fail the run; controller tests use `fakeAsync`. Backend tests reset DB + limiters per test via importlib.reload fixtures (`backend/tests/conftest.py`).

## Phase B (Quick Settings SOS Tile) invariants

- `SosTileService.kt` is a PURE trigger with zero SOS logic: `onClick` launches the app with `guardianher://tilesos` (`startActivityAndCollapse`, PendingIntent variant on API 34+), and the EXISTING pipeline arms. There is exactly one SOS implementation — never add a second.
- **The launch MUST be explicit** (`Intent(this, MainActivity)` + `HomeWidgetLaunchIntent.HOME_WIDGET_LAUNCH_ACTION` + data URI, mirroring `ShakeSosService`): MainActivity declares NO `guardianher://` intent-filter, so an implicit ACTION_VIEW throws ActivityNotFoundException, and the home_widget plugin only captures cold-start URIs carried by its own launch action. The PendingIntent uses dedicated request code 4242 because PI matching ignores data URIs (code 0 could return the widget's `guardianher://sos` record).
- **Locked-screen behavior (Android 14/Motorola Edge 30, verified)**: unlocked taps work with the process dead or alive; locked taps work when the Flutter process is ALIVE (activity starts invisibly behind the keyguard and Dart arms SOS); a COLD start behind a secure keyguard is silently refused by ATS (no START record at all). `onClick` therefore branches on `KeyguardManager.isKeyguardLocked` → `unlockAndRun { dispatch() }`, the documented TileService API — the user sees the unlock prompt and SOS arms immediately after unlocking. No BAL bypasses (overlay/accessibility/etc.) are used or permitted.
- `guardianher://tilesos` is an ARMING trigger like `guardianher://shakesos`: `home_widget.dart` routes it to `/sos` AND invokes the shared arm callback (now named `onEmergencyTrigger`; widget taps still navigate only). Duplicate taps are absorbed by SosController's state machine ("second startSos while armed is ignored") — do not add tile-level dedup logic in Kotlin.
- **SOS side-effect coordination is APP-ROOTED, not screen-scoped**: `GuardianHerApp.build()` watches `sosActionsControllerProvider`. Cold-start triggers arm from the routing callback BEFORE any screen mounts, and SOS activates instantly (zero countdown is a deliberate product decision), so a coordinator built lazily by `SosScreen` misses every transition — no vibration, no alert notification, no location FGS, no tile mirror. Do not remove the root watch.
- Tile state is a one-way MIRROR: Dart pushes a boolean through `guardianher/sos_tile` (`setSosEngaged`) from `onSosStateChanged` plus an initial sync on every `SosActionController.build()` (corrects a stale "engaged" flag left by force-stop/crash mid-SOS; until the app reopens after such a death, the tile may honestly show stale state — Kotlin cannot know the truth). Kotlin persists it to prefs and reads it in `onStartListening`. The tile exposes nothing else (no location, contacts, ids).
- The service must stay `exported="true"` + `BIND_QUICK_SETTINGS_TILE` (system-only binder). No new app permissions were added.

## Phase C (Safe Journey) invariants

- `lib/features/journey/` wraps the shared SafetySession ledger (`SafetySessionMachine`, type `safe_journey`) and delegates ALL tracking to the existing LiveLocation machinery — the journey owns NO tracker, NO FGS, NO backend surface. Journeys ride `LiveShareDuration.minutes120` + `LiveUpdateInterval.normal` (30 s = the top of the approved 15–30 s clamp; the backend's closed sets {15,30,60,120}/{10,30} are untouched — no backend changes).
- **Escalation is a transformation, never a second session.** `JourneyController` (APP-ROOTED: `GuardianHerApp.build()` watches `journeyControllerProvider`, same pattern as the SOS side-effect coordinator) listens to `sosControllerProvider`; when SOS engages during an active journey it closes the journey's OWN share (`_ownedLiveSessionId` guards ownership so it never kills a session it did not start), then explicitly calls `live.startEmergency()` — idempotent under LiveLocationController's single-session guard, so every interleaving with `SosActionController._activateEffects` yields exactly ONE emergency share. The ledger records one completed session with `JourneyEndReason.escalatedToSos`; there is no auto-resume after the emergency ends (start again deliberately).
- Starting is REFUSED while SOS is engaged (honest notice on the idle form); duplicate starts are absorbed by the state machine; SOS has absolute priority.
- Share-link expiry flags `shareExpired` (banner + "Share a new link") but does NOT end the journey — the user may still be travelling. Ownership check is by EXCLUSION (`_ownedLiveSessionId != null`), because terminal live transitions drop the session object.
- Vehicle info (`VehicleInfo`) is OPTIONAL, in-memory ONLY (never persisted, never logged — toString hides contents), displayed on the journey screen; attachment to emergency messages is deferred to later phases.
- `buildJourneyShareMessage` keeps Phase 3G wording discipline: describes what the user chose to share + expiry time, never claims monitoring/sending. Sharing uses the system share sheet + clipboard copy only (non-emergency convenience).
- Widget tests that start a journey MUST tear it down before finishing (`endJourney` + `stopSession`) or pending live-upload/TTL timers fail the run (same discipline as mid-SOS tests).

## Phase D (Vehicle Information) invariants

- `VehicleInfo` lives in `lib/features/journey/domain/vehicle_info.dart` (v2): `VehicleType` is a CLOSED enum {auto, taxi, cab, bus, privateVehicle, other} with friendly labels (`label` getter) — UI copy must never expose enum names. Optional fields: registrationNumber / driverName / bookingReference; everything stays IN-MEMORY ONLY (never persisted, never logged; toString hides contents).
- Registration normalization is pure and in `vehicle_registration.dart`: `normalizeRegistration` canonicalizes recognized shapes (classic Indian `DL01AB1234`, BH-series) case/separator-insensitively; UNRECOGNIZED plates pass through VERBATIM — never force foreign/manual formats into Indian shape. `formatRegistration` pretty-spaces for display only. Invalid input returns a reason key (`empty`/`tooLong`/`invalidCharacters`) for inline form errors, not exceptions.
- `JourneyController._sanitize` is defense-in-depth: whatever reaches the journey is stored CANONICAL + trimmed + clamped to 60 chars regardless of caller (`_maxOptionalFieldLength = 60`; the internal `clean` closure passes null/empty through untouched and returns the SAME instance when nothing changed). Unrecognized plates are NOT reshaped here either — sanitize mirrors the normalizer's verbatim rule. The journey screen ALSO normalizes before start (fast-entry UX: typing `dl-01-ab-1234` stores/displays `DL 01 AB 1234`).
- **Emergency vehicle context bridge**: `emergencyVehicleContextProvider` (in-memory StateProvider) is published at journey START and survives SOS ESCALATION so the SOS screen can show the vehicle without re-entry; it is RELEASED when the SOS settles (SosCompleted/SosIdle after `_vehicleHandedToSos`) or on dismiss if never handed over. A NEW journey never inherits the previous vehicle.
- Share messages include the vehicle section ("Vehicle: <label>" + "Registration: <spaced>") ONLY when explicitly passed — driver name and booking reference are NEVER included in any share body, URL, log line, or analytics event; registration numbers must never appear in URLs (enforced by test).
- The completed-journey summary snapshots startedAt + vehicle into `JourneyCompleted`; dismissing the summary destroys the data (session-scoped by design).
- Safety Recorder seam: `safety_recorder_events.dart` defines the privacy-safe event types with `SafetyEventMetadataKey` constants (type + boolean/enum metadata only, sessionId truncated in toString). Phase E implementation lives in `lib/features/safety_recorder/` with `SafetyRecorderController` observing all feature providers.
- Test infra: `FakeLiveLocationUpdates.startUpdates` hands out a FRESH single-subscription stream per call but controllers are swapped, NEVER closed — `StreamController.close()` does not complete under fakeAsync and would deadlock `_teardownTracking`'s awaited FGS stop (fgs.stopCount would stay 0).

## Phase E (Safety Recorder) invariants

- **Architecture**: `SafetyRecorderController` (Riverpod `Notifier`) is the SINGLE entry point for all event recording. It holds a rolling in-memory buffer (max 500 events, 10-minute window) that is frozen into a `SafetyIncident` on SOS activation. The controller observes `sosControllerProvider`, `journeyControllerProvider`, `locationControllerProvider`, `sosActionsControllerProvider`, and `checkInControllerProvider` via `ref.listen`; the app root (`GuardianHerApp`) watches `safetyRecorderProvider` to keep the controller alive across navigation.
- **Event types** are in `safety_recorder_events.dart` (closed enum `SafetyEventType`): `shakeDetected`, `sosActivated`, `sosCancellationStarted`, `sosCompleted`, `locationCaptureStarted`, `locationCaptured`, `locationUnavailable`, `locationTimeout`, `locationPermissionDenied`, `locationServicesDisabled`, `locationUpdated`, `communicationAttempted`, `communicationFailed`, `communicationHandedOff`, `journeyStarted`, `journeyEnded`, `vehicleAttached`, `sessionStarted`, `sessionCompleted`, `sessionExpired`, `checkInStarted`, `checkInCompleted`. Each maps to a `SafetyEventCategory` via `categoryForEventType`.
- **Metadata** uses `SafetyEventMetadataKey` string constants (never raw strings): `vehicleType`, `hasRegistration`, `accuracyMeters`, `isStale`, `failureCategory`, `channelType`, `endReason`. Values are strings only; no nested objects.
- **Incident lifecycle**: `recording` (active SOS) → `frozen` (SOS cancelled/completed) → `completed` (persisted). Only three statuses exist. `isActive` is true for `recording`/`frozen`; `canVerifyIntegrity` is true only for `completed` with events.
- **Hash chain**: `incident_integrity.dart` implements SHA-256 chaining from `incidentGenesisHash` (`guardianher-recorder:v1`). Each hash binds `eventId + eventType + occurredAt` to the previous hash. Metadata is deliberately NOT in the chain (hash proves event sequence integrity, not metadata immutability). `verifyIncidentIntegrity` is a pure function; `SafetyIncident.verifyIntegrity()` wraps it.
- **Repository**: `SafetyIncidentRepository` (abstract) with `SafetyIncidentRepositoryImpl` (SharedPreferences-backed JSON). Serialization via `safety_event_serializer.dart` (JSON map with string values only).
- **Retention**: max 20 incidents, eviction in `SafetyRecorderController._loadIncidents` after load. Single eviction point — no duplicate cleanup.
- **Privacy**: NO coordinates, phone numbers, emails, message bodies, vehicle registrations, or PII in any event metadata, toString, or serialized output. Event IDs are `generateRecorderEventId()` (32-char hex). Session IDs are opaque. Test file `safety_recorder_privacy_test.dart` enforces these invariants.
- **Shake integration**: `app.dart` records `shakeDetected` in the `onEmergencyTrigger` callback BEFORE calling `startSos()`, only for `guardianher://shakesos` URIs (detected via `isShakeSosUri`).
- **Location events** are recorded by the controller via `ref.listen(locationControllerProvider)` — only during an active incident. The controller checks `previous.status != next.status` to deduplicate.
- **Communication events** are recorded via `ref.listen(sosActionsControllerProvider)` — only when `lastOutcome` changes during an active incident. Channel type is extracted from the `SosCommunicationOutcome` string.
- **Check-in events** are recorded via `ref.listen(checkInControllerProvider)` — only when the status message changes during an active incident.
- **Failure isolation**: recorder failures never block, delay, or affect any safety feature. The controller catches and logs all exceptions. `safety_recorder_failure.dart` exists as an empty file (dead code, no imports).
- **Tests**: `safety_recorder_controller_test.dart` (unit), `safety_incident_test.dart` (model + integrity), `safety_recorder_integration_test.dart` (lifecycle flows), `safety_recorder_privacy_test.dart` (PII invariants), `safety_recorder_screen_test.dart` (presentation). Flutter not available in remote — run `flutter test` locally.

## Security

GuardianHer V1 does not provide an application-level PIN or biometric lock. The application prioritizes immediate emergency access, so it opens directly to Home with no authentication gate on launch, resume, or deep-link. Sensitive data (trusted contacts, emergency history) is still stored via `SecureStorageService` (Keystore-backed); do not replace secure storage with `SharedPreferences` and do not reintroduce an app lock/authentication layer.
